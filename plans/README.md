## Dependency notes

- **001 before 003 (soft)**: 003 cuts onboarding friction; 001's funnel is
  how you prove it worked. Not a hard blocker — 003's `hasReceivedEvents`
  flag uses `usage_counters`, which exists today.
- **002 informs, does not block, everything**: it is a design/spike whose
  output is a decision document, not shipped code. A future build plan for
  the managed proxy should be commissioned only after 002's go/no-go.
- 004 and 005 are independent of each other and of 001–003.

## Findings considered and rejected

- **OS/device/geo segmentation**: not collected today (events carry only a
  truncated browser family + major UA). Adding new dimensions is a privacy
  posture change disguised as a feature; deferred to an explicit decision.
  Plan 004 ships browser-only with zero new collection.
- **Public per-browser report pages**: interacts with the sealed
  `daily_provider_stats` rollup and multiplies small-count cells below the
  publish floor. Deferred; 004 is account-dashboard-only.
- **CI-pushed detector health (DB table + authenticated ingest from
  GitHub Actions)**: rejected for plan 005 in favor of on-demand probing
  with a 15-min cache — no migration, no new secret, always fresh.
- **blockrate-hosted shared proxy domain** (as a remediation shortcut):
  violates the first-party invariant the moment the domain lands on a
  filter list — the exact failure class the reporter architecture exists to
  prevent. Recorded as a rejected alternative inside plan 002's required
  design doc.
- **Auto-editing user projects in `blockrate-init`** (client-snippet
  injection): too destructive for v1 of a scaffolding tool; create-only.
  Noted as follow-up in plan 003.
